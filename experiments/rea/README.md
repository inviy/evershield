# Does evershield stop REA?

[REA](https://github.com/morluto/rea) reverse engineers apps from the
outside: it reads built bundles, attaches to a browser over the DevTools
Protocol, captures the DOM, scripts and source maps, and hands the result to
an AI agent. It cannot be detected or blocked; to the server it is a normal
visitor. So the honest question is not "does evershield block REA" but
**"after evershield passes, does REA still get anything worth having?"**

This experiment answers that with REA itself.

## What it does

`run.mjs` builds one small app twice:

- **leaky**: a Stripe secret key and an internal API address in the bundle,
  production source maps, an API that returns Pro metrics to free users, and
  a page that hides them with `filter: blur()`.
- **fixed**: the same app after following evershield's remediation: key
  moved server-side, internal URL removed, source maps off, the API withholds
  Pro fields for free users, and the page renders `●●●●` placeholders.

For each build it serves the app on 127.0.0.1, opens it in headless Chromium
as a free user, and runs REA 6.5.0 the way an attacker would:
`inspect-web-page` (DOM, accessibility text, script sources, storage keys),
`analyze-web-bundle --fetch-source-maps`, and
`analyze-javascript-application` on the build output. Then it runs
`evershield scan`, `audit` and `surface` on the same build and server.

## Result

See [results.md](results.md) (regenerated by every run):

| Leak | Recovered from the leaky app | evershield flags it | Recovered after the fix |
|---|---|---|---|
| Stripe secret key in the bundle | yes (rea inspect, rea bundle, rea static) | `artifact/secret-like-string` critical/high | no |
| Internal API address in the bundle | yes (rea inspect, rea bundle, rea static) | `artifact/internal-endpoint` medium/medium | no |
| Original source via a published source map | yes (rea bundle) | `artifact/source-map-published` high/high | no |
| Pro metric in the free user's page, hidden by blur | yes (rea inspect, accessibility text) | `surface/hidden-higher-tier-content` high/high, `surface/obscured-content` high/medium | no |
| Pro fields in the free user's API response | yes (the free user's response) | `response/expected-absent-field-present` high/high | no |

evershield findings on the fixed app: **0**.

Every leak REA recovered, evershield had flagged; after the fix REA
recovered none of them. The run also caught a false positive in evershield
itself: the first version of `surface/obscured-content` flagged the
recommended fix ("Burstiness score ●●●●" behind a blur). That is fixed, and
the fixed app now passes cleanly.

## What this does not show

- **REA still works on the fixed app.** It still reconstructs modules,
  routes, field names and UI structure. Client code is public by nature;
  evershield makes sure what ships is safe to be public, not invisible.
- The API row is measured on the free user's raw response. REA's passive
  window opened after the page had fetched, so REA's own capture missed that
  body; DevTools, `curl` or a REA scenario started before navigation see it.
- The internal address is medium severity, below the default gate. It is
  reported, but does not fail a build unless you lower `--fail-on`.
- One small demo app. The [false-positive corpus](../../docs/corpus.md)
  covers real-world code; this covers what an attacker actually gets.

## Reproduce

```bash
pnpm build                 # in the repository root
cd experiments/rea
npm install
CHROMIUM=/path/to/chrome node run.mjs
```

The fake key is assembled at runtime, so no secret-shaped string is ever
committed; `results.*` record only which leaks were recovered.
